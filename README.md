# ACIS — Agentic Code Intelligence

**Ask a question in plain English, get back the most relevant code from a large codebase — ranked, with the exact
source as evidence.** ACIS runs locally on a CPU, offline, with no API keys. It *retrieves and ranks* existing code; it
never generates code.

Built for the Samsung PRISM GenAI Hackathon, Theme 1 (*Agentic Code Intelligence*): **P0** retrieval accuracy on the
CoIR *AppsRetrieval* benchmark through MTEB, **P1** retrieval across code versions, and the **Bonus** evolutionary
retrieval across all versions.

> **Official P0 result — CoIR AppsRetrieval TEST split, generated by MTEB: NDCG@10 = 78.283 · MRR@10 = 74.393.**
> The MTEB-generated `appsretrieval_results.json` is attached to the [GitHub Release v1.0.0](https://github.com/abhinavakku513-collab/Agentic_Code_Intelligence/releases/tag/v1.0.0)

## 1. What problem does ACIS solve?

Imagine a codebase with thousands of programs. You type:

> *"Given a list of workers with a quality and a wage expectation, hire exactly k of them at minimum total cost."*

ACIS searches every program and returns the ones that solve that problem, best first, each with its source code.

That is **code retrieval**: a natural-language query goes in, a ranked list of existing code snippets comes out.
ACIS does **not** write, explain or modify code — the Theme 1 guidelines put generation out of scope, and ACIS has no
language model in its ranking path.

## 2. What is P0?

**P0 = retrieval accuracy**, the first and most important Theme 1 goal. It is measured on the **CoIR AppsRetrieval**
dataset: 8,765 Python programs (solutions to programming problems from APPS) and natural-language problem statements.
For each problem statement exactly one program is the correct answer.

Two numbers score a ranking (higher is better, 0–100):

- **NDCG@10** — *is the right program near the top of the first 10 results?* Full marks if it is #1, partial credit
  at #2–#10 (less the lower it is), nothing below #10.
- **MRR** (mean reciprocal rank) — *how far down do you have to read?* 1 if the right program is #1, ½ if #2, ⅓ if #3,
  and so on, averaged over all queries.

**DEV vs TEST.** The dataset has a **train** split (5,000 queries) and a **test** split (3,765 queries). We use the
train split as our development set ("DEV") for every decision. The **TEST** split is the official screening set: its
answer labels are kept sealed outside this repository and are read only by the official MTEB run. We never tune on
TEST.

## 3. Architecture

This is the pipeline the code actually runs — one function (`AcisEngine._rank_one`) serves the CLI, the web API/UI
and the MTEB evaluation alike.

```
Natural-language query
  │
  ▼  1. Query preparation      normalise text · detect query type (problem statement vs. short question / identifier)
  │
  ▼  2. Four retrieval passes, run independently over the whole corpus
  │     ├─ semantic   gte-modernbert-base      (dense embeddings, exact search)   → top 300
  │     ├─ semantic   Qwen3-Embedding-0.6B     (dense embeddings, exact search)   → top 300
  │     ├─ lexical    BM25 with a code-aware tokenizer                            → top 200
  │     └─ exact      identifier / symbol index (e.g. `dijkstra`, `heapq.heappush`) → top 50
  │
  ▼  3. Candidate union        ≤ 500 candidates (reciprocal-rank cut); every candidate is then scored by EVERY channel
  │
  ▼  4. Ranking                problem statements → LightGBM LambdaRank over 34 evidence features
  │                            (both cosines and ranks, gte/Qwen agreement, BM25, identifier hits, I/O literals, length …)
  │                            other queries → weighted fusion (Qwen + gte dense, BM25); a lone identifier → exact matches first
  │
  ▼  5. Verified code          every result is re-read from a content-addressed store by its hash (nothing is generated)
  │
  ▼  Ranked results (+ per-channel evidence, stage timings, calibrated confidence)
```

## 4. Why multiple retrieval methods?

Each method sees a different kind of similarity, so each one finds programs the others miss:

- **Semantic retrieval (embeddings)** understands meaning: *"shortest route between cities"* matches a Dijkstra
  implementation that never uses the word "route". ACIS runs **two** embedding models because they make different
  mistakes: on DEV, Qwen3 has the right program in its top 100 for 256 queries where gte misses it, and gte for 20
  where Qwen misses it ([evidence](docs/evidence/p0/encoder_diagnostics_gte_base.json)).
- **Lexical retrieval (BM25)** matches the exact words and numbers in the query — constants, output strings,
  variable names a problem statement mentions.
- **Exact identifier retrieval** answers queries that name code directly (`UnionFind`, `heapq.heappush`).

The ranker then weighs all of this evidence together. On DEV, the union of the four lists contains the right program
for **99.38 %** of queries ([evidence](docs/evidence/p0/union_marginal_recall.json)), so the remaining errors are
mostly about *ordering*, which is what the learned ranker is for.

## 6. P0 results

### DEV (APPS train split, all 5,000 queries, full 8,765-document corpus)

Learned components are scored **out of fold** (each fold ranked by a model trained on the other four), through the
same `AcisEngine._rank_one` the product runs.

| System | NDCG@10 | MRR@10 | Recall@100 | Evidence |
|---|---|---|---|---|
| gte-modernbert-base, dense only (baseline) | 71.03 | 67.46 | 93.78 | `[ledger:dev-a674159a4324]` |
| previous ACIS pipeline (gte + BM25 + symbols + ranker) | 74.13 | 70.93 | 94.86 | `[ledger:dev-299a3010be5a]` |
| Qwen3-Embedding-0.6B, dense only | 84.41 | 81.63 | 98.50 | [encoder diagnostics](docs/evidence/p0/encoder_diagnostics_gte_base.json) |
| ACIS + Qwen3 (second encoder, refit ranker, Qwen-weighted fusion) | 86.70 | 84.19 | 98.72 | `[ledger:dev-f93aeb265be7]` |
| **ACIS final pipeline** (+ gte/Qwen agreement features) | **87.07** | **84.72** | **98.76** | `[ledger:dev-839fba9f81a6]` |

Final vs the previous ACIS pipeline: **+12.94 NDCG@10** (CI [+12.15, +13.73]) and **+13.79 MRR@10** ([+12.90, +14.67]); the last step alone (encoder-agreement
features) adds +0.37 NDCG@10 (95 % CI [+0.11, +0.64]) and +0.53 MRR@10 ([+0.19, +0.87]) — paired bootstrap, 10,000
resamples. Where the remaining DEV errors are: 3,968 queries have the right program at #1, 749 at #2–10,
252 lower but inside the candidate pool (ranking errors), 31 outside it (retrieval errors) —
[failure buckets](docs/evidence/p0/failure_buckets.json). All measurements: [docs/evidence/p0](docs/evidence/p0/README.md).

## 7. How to install

You need: **Linux, macOS or Windows with WSL2**, **Python 3.11 or 3.12**, about **10 GB free disk**, **8 GB RAM**
(16 GB recommended), and [`uv`](https://docs.astral.sh/uv/) (one-line install:
`curl -LsSf https://astral.sh/uv/install.sh | sh`). No GPU is needed.

```bash
git clone https://github.com/abhinavakku513-collab/Agentic_Code_Intelligence.git
cd Agentic_Code_Intelligence
make setup        # creates .venv from the hash-locked uv.lock (CPU-only PyTorch)
make fetch        # downloads the APPS corpus (the only data download)
make models       # downloads both encoders at their pinned commits and re-verifies every file hash
```

`make` not available? Run the commands it wraps: `uv sync`, `uv run acis fetch`,
`uv run acis fetch --models gte-modernbert-base,qwen3-embedding-0.6b`.

**Skip hours of first-time embedding (recommended).** Embedding the 8,765 programs with both models takes hours on a
CPU. The Release ships the document vectors as two checksummed packs; import them once:

```bash
# download acis-demo-index.zip and acis-demo-index-qwen.zip from the GitHub Release into dist/, then:
uv run acis demo-index import dist/acis-demo-index.zip
uv run acis demo-index import dist/acis-demo-index-qwen.zip --encoder qwen3-embedding-0.6b
```

Each import verifies the checksums and the model fingerprint and recomputes 1 % of the vectors (must match at cosine
≥ 0.9999). The packs only fill the local vector cache: the official evaluation never reads them.

## 8. How to run

```bash
uv run acis serve                 # API + demo web page on http://127.0.0.1:8000/
```

It is ready when `curl -s http://127.0.0.1:8000/readyz` shows `"p0_corpus": true` (about a minute after start with the
vector packs imported). The scripted end-to-end walkthrough (P0 search, P1 commits and rollback, Bonus evolution) is
`make demo`.

## 9. How to search

```bash
uv run acis search "find the shortest path in a weighted graph using a priority queue" --top-k 5
```

The output names the encoders, the query route and the stage that ordered the list, per-stage timings, and for each
hit its similarity, its rank in each channel, its id, content hash and first line of code. Over HTTP:

```bash
curl -s -X POST localhost:8000/v1/search -H 'content-type: application/json' \
  -d '{"query":"reverse a linked list","top_k":3,"explain":true}'
```

## 10. How to reproduce the P0 evaluation

The official recipe from the Theme 1 guidelines, implemented in `src/acis/mteb_adapter.py`
(`PrePostPipelineEncoder(AbsEncoder)`), is:

```python
import os
os.environ["ACIS_CONFIG"] = "configs/official.yaml"   # the submission configuration (Mode A, strict, CPU)

import mteb
from acis.mteb_adapter import PrePostPipelineEncoder, write_official_json

model = PrePostPipelineEncoder()                      # Mode A = the full ACIS pipeline (ACIS_MODE=B: dense-only surface)
task = mteb.get_task("AppsRetrieval")
result = mteb.evaluate(model, [task], encode_kwargs={"batch_size": 64}, cache=None, overwrite_strategy="always")
write_official_json(list(result.task_results)[0], "appsretrieval_results.json")   # json.dump(task_result.to_dict())
```

You do not need to type it — one command runs it, **cold** (no cached vectors, so the timing is honest) and strict:

```bash
make reproduce                    # = acis eval official --config configs/official.yaml --cold --strict --reproduce
uv run acis eval verify-submission --run-dir runs/reproduce
```

It downloads the AppsRetrieval task through MTEB, embeds the corpus and the 3,765 test queries with both encoders,
ranks them with the full pipeline and writes `runs/reproduce/appsretrieval_results.json`. **On an 8-core CPU expect
about 8 hours** (the submitted run took 27,849 s; Qwen3 dominates the time) and about 6–7 GB of RAM; let it finish
uninterrupted and keep the machine from sleeping.
`write_official_json` is `json.dump(task_result.to_dict())` with a datetime-safe encoder — the guidelines' sample
crashes on the result's `date` field. `cache=None, overwrite_strategy="always"` stops MTEB from returning a stale
cached result.

The DEV numbers in section 6 are reproduced (with cached vectors, minutes) by:

```bash
uv run python scripts/bench/eval_pipeline.py --no-route-analysis     # all 5,000 DEV queries, out of fold
```

## 12. P1 — retrieval across versions

Codebases change with every commit. ACIS keeps an **immutable snapshot per version**: a new commit only embeds the
code units that actually changed (everything else is reused by content hash), the new version is validated and then
activated atomically, and any version can still be searched or rolled back to instantly.

```bash
uv run acis ingest <git repo | directory | .zip | .jsonl> --repo myrepo    # builds every version it contains
uv run acis versions --repo myrepo
uv run acis search "parse the config file" --repo myrepo --version <v>
uv run acis rollback --repo myrepo
```

Measured: a 1- or 10-unit change is searchable in about 2 s (p95) `[ledger:bench-9153e49050de]`; incremental builds are
tested to equal from-scratch builds, and recovery after `kill -9` and rollback are covered by the test suite.

## 13. Bonus — evolutionary retrieval

Across many versions the same function appears again and again with small edits, which floods a flat result list
with near-duplicates. `acis evolve` aligns revisions into **lineages** (identical → moved → renamed → inferred, each
step evidence-gated) and returns **one answer per lineage** with its best-matching revision and a timeline (reverts
named).

```bash
uv run acis evolve "sort an array" --repo myrepo --top-k 5 --flat
```

Measured honestly: lineage recovery is exact on our benchmark and grouping removes the duplicates; grouped and flat
ranking **tie** on Evolution-NDCG@10 `[ledger:bench-52d48f680740]`, so no ranking gain is claimed.

## 14. UI

`acis serve` opens a web page with four tabs: **Search** (P0, with per-hit evidence from every channel), **Versions**
(P1 commits and rollback), **P0 evaluation** (the official TEST result and, separately, the DEV evaluation — each
rendered from its own ledger row) and
**Evolution** (Bonus).

> **The web UI is a demonstration and visualization interface designed for convenient hands-on presentation.**
> **The UI is not a separate retrieval implementation:** it calls the same backend engine (`AcisEngine`) as the CLI.
> **The underlying CLI/backend is the actual ACIS system.** All benchmark evaluation is performed through the
> reproducible evaluation/CLI pipeline (section 10), **not through the UI.**

What the page shows about the pipeline (which channels ran, which stage ordered the list, which encoders are loaded)
is read from the live engine for that request; a component that did not run is not shown as running.

## 17. Reproducibility

- **Pinned everything:** `uv.lock` (hash-locked dependencies, CPU-only PyTorch), model commits + per-file SHA-256
  (`configs/models/`), dataset revision (`CoIR-Retrieval/apps@f22508f9…`), the ranker file in the repository.
- **One configuration for the submission:** `configs/official.yaml` (Mode A, strict, CPU, fp32). Its ranking-relevant
  keys are hashed into the MTEB model revision `<git12>+<config12>`, so a result always names the exact code and
  configuration that produced it.
- **Honest cold run:** the official run starts from empty caches; its `evaluation_time` is never a warm time.
- **Every number has evidence:** `runs/ledger.jsonl` is hash-chained (`uv run acis verify` checks it); DEV
  measurements are in `docs/evidence/p0/`.
- **Deterministic:** same snapshot, configuration and thread count give the same ranking (tested).
- **Tests:** `make test-fast` (quick suites) · `make test` (everything).
